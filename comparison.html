workflow-agent vs OpenSpec

Both preserve AI-assisted work as Markdown in your repository. They solve different primary problems: workflow-agent manages delivery across tickets; OpenSpec manages agreement about system behavior.

Compared against workflow-agent’s repository and OpenSpec 1.14.1 documentation · reviewed 12 October 2026

The short answer

Choose the source of truth you actually need.

Choose workflow-agent when your pain is decomposing a change, sequencing deployable tickets, verifying implementation phases, and resuming delivery. Choose OpenSpec when your pain is agreeing on requirements and scenarios, maintaining living product specs, or standardizing a customizable spec process across tools and teams.

Do not run both for the same change.

Two proposals, two task lists, and two completion states create drift. Pick one owner; use the other only for a clearly separate concern.

02 · Daily development flow

What using each one feels like

workflow-agent asks you to manage delivery explicitly. OpenSpec asks you to make behavior explicit, then keeps planning artifacts fluid while the implementation evolves.

workflow-agent

Change → tickets → verified phases

  1. Open a workspace

    wf new creates a change with context, status, and four ticket-state folders.

  2. Clarify the work

    wf discover turns notes into goals, scope, constraints, risks, and rollout context.

  3. Split delivery

    wf breakdown proposes 1–3 day, independently deployable tickets. You confirm before files are created.

  4. Specify when useful

    wf specify confirms one ticket’s user stories, scenarios, protected behaviors, and exclusions just before planning.

  5. Plan one ticket

    wf plan explores actual code and writes detailed, independently verifiable phases plus a short human brief.

  6. Implement one phase

    wf implement … phase N changes only that phase, runs its verification, and records evidence or deviations.

  7. Complete deliberately

    Optional review checks the code. wf complete checks readiness, final verification, acceptance criteria, and specification coverage before moving the ticket to done.

OpenSpec · core profile

Agreement → implementation → living specs

  1. Explore when uncertain

    /opsx:explore investigates code and options without writing code or artifacts unless you ask.

  2. Propose the change

    /opsx:propose creates proposal, delta specs, design, and tasks in one pass.

  3. Review and revise

    Read the artifacts. Edit Markdown directly or use /opsx:update to reconcile related planning files.

  4. Apply tasks

    /opsx:apply implements unchecked tasks and marks them complete. Re-running resumes from the checklist.

  5. Verify if enabled

    The expanded /opsx:verify checks completeness, correctness, and coherence. It reports rather than blocks.

  6. Sync and archive

    Delta specs merge into current specs, then the full change moves into a date-stamped archive. Incomplete tasks warn but do not block archive.

Practical difference: workflow-agent executes one verified phase at a time, checks readiness when completing tickets, then archives any terminal change as a previewed synthesis with an explicit outcome. OpenSpec is task-checklist driven; its optional verifier reports mismatches, and archive preserves the full artifact set while remaining intentionally non-blocking.
03 · Files and persistence

What survives the chat session

The file shape determines what a future developer—or a fresh agent context—can reconstruct.

workflow-agent

CONTEXT.md

Change-level goals, boundaries, risks, and decisions.

STATUS.md

Derived summary across all tickets; folder location remains authoritative.

TICKET.md

Stable goal, scope, acceptance criteria, dependencies, risk, and technical context.

SPEC.md

Optional confirmed ticket-level user stories, observable scenarios, protected behaviors, and exclusions.

PLAN.md

Code-grounded implementation source of truth, organized into verifiable phases.

PLAN-BRIEF.md

Concise human explanation of architecture, data flow, decisions, rollout, and risks.

PROGRESS.md

Actual changes, commands/results, deviations, blockers, and follow-up work.

REVIEWS.md

Dated optional plan and implementation reviews.

archive/*/SUMMARY.md

Dated terminal outcome, current invariants, lasting decisions, stable code map, limits, evidence, and references.

OpenSpec

proposal.md

Why the change matters, what changes, and expected impact.

specs/**/*.md

ADDED, MODIFIED, REMOVED, or RENAMED requirements with scenarios.

design.md

Technical approach, decisions, and implementation shape.

tasks.md

Implementation checklist and resumable completion state.

.openspec.yaml

Change metadata such as schema and creation date.

openspec/specs/

Durable baseline of current system behavior, updated by sync/archive.

changes/archive/

Date-stamped completed changes preserving all planning artifacts.

History versus current truth: workflow-agent retains detailed execution evidence per ticket. OpenSpec’s distinctive asset is the separate baseline spec set that describes the system after changes are merged.
04 · Strengths and weaknesses

Pros, cons, and hidden costs

workflow-agent · strengths

  • Handles an epic, not just one proposal. A change can be decomposed into multiple deployable tickets with dependencies and explicit states.
  • Strong execution discipline. Plans contain independently verifiable phases; progress records commands, results, and deviations.
  • Human-readable plan layer. The full implementation plan and concise plan brief serve different review needs.
  • Explicit review gates. Separate plan and implementation reviews are available without being mandatory.
  • Low operational footprint. One Agent Skill and Markdown files; no CLI daemon, schema engine, or telemetry.
  • Worktree flow is integrated. Any command can opt into a validated isolated worktree and optional frozen dependency installation.
  • Good external tracker fit. Change and work-item IDs can map naturally to existing issue IDs.

workflow-agent · weaknesses

  • No product-wide behavior baseline. Ticket specifications remain with delivery history rather than merging into a canonical current domain spec.
  • More lifecycle ceremony. New, discover, breakdown, optional specification, plan, phase implementation, and completion are explicit operations.
  • Less fluid by design. Material plan contradictions stop for user input; this protects scope but interrupts exploratory implementation.
  • Narrower integration surface. It depends on Agent Skills and required tool capabilities rather than generating adapters for many assistants.
  • Customization is manual. Templates and references can be edited, but there is no declarative schema/config system.
  • Small ecosystem. Fewer community examples, integrations, and contributors than OpenSpec.

OpenSpec · strengths

  • Specs remain useful after delivery. Delta requirements merge into domain-organized baseline specs describing current behavior.
  • Requirements are test-shaped. SHALL-style requirements and concrete scenarios make behavior and edge cases reviewable.
  • Easy iteration. Artifacts remain editable during implementation; /opsx:update reconciles the plan coherently.
  • Broad tool support. openspec init generates tool-specific commands or skills for a large documented matrix.
  • Deep customization. Project context, artifact rules, operation guidance, custom schemas, templates, and global overrides are first-class.
  • Team and multi-repo direction. Stores can centralize plans and shared specs outside code repos, though the feature is beta.
  • Deterministic CLI assistance. The CLI owns scaffolding, status, validation, artifact instructions, and archive mechanics.

OpenSpec · weaknesses

  • Two interaction surfaces. Setup/status use a terminal CLI; implementation flows run as assistant commands whose spelling varies by tool.
  • Verification is not default. The core profile omits /opsx:verify, and verification reports do not block archive.
  • Weaker multi-ticket project model. One change is one work unit; there is no equivalent nested ticket lifecycle with dependency readiness.
  • Spec maintenance is real work. Baseline specs become valuable only if the team keeps deltas accurate and resolves drift before archive.
  • More generated/configured surface. CLI version, profiles, schemas, tool adapters, and generated command files need updates.
  • Telemetry defaults on. Only command names and version are documented as collected, but privacy-sensitive teams must opt out.
  • Fluidity shifts discipline to the team. Incomplete tasks warn rather than block archive; scope control and artifact honesty remain human responsibilities.

06 · Decision guide

Choose using the failure you want to prevent

Choose workflow-agent if…

  • Large work gets lost between tickets or sessions.
  • You need explicit draft, ready, in-progress, and done states.
  • You want implementation split into verified phases with recorded evidence.
  • You already have Jira/Linear/GitHub issues and need local execution structure rather than another requirements system.
  • Plan and code review checkpoints matter more than a long-lived behavior catalog.
  • Agent-created Git worktrees are part of your normal flow.
  • You prefer one skill and almost no runtime footprint.

Choose OpenSpec if…

  • Vague or drifting requirements are the dominant source of rework.
  • You need a versioned answer to “what does the system do now?”
  • Behavioral scenarios should survive after a feature ships.
  • Many developers and AI tools need the same standardized workflow.
  • Your team wants to design or fork its own artifact graph.
  • Features span repositories or teams and you can accept beta Stores risk.
  • You value fluid plan revision more than enforced lifecycle gates.

Do not choose either by default for trivial work

A one-line typo, dependency bump, or obvious local fix may not justify durable planning files. Use a workflow when misunderstanding, coordination, interruption, or future context loss costs more than the added ceremony.

If both are already installed in one project

Recommended cutover: select one owner per change.

Do not mirror a change into both .workflow/ and openspec/changes/. Their plans and completion state will diverge because neither tool synchronizes the other.

For a delivery-heavy project with external product requirements, use workflow-agent as the change owner and keep product/API contracts in the project’s existing documentation. For a contract-heavy product where current behavior must remain queryable, use OpenSpec as the change owner and rely on your issue tracker for portfolio/ticket status.

If you still need both at repository level, define a hard boundary: for example, OpenSpec owns cross-team behavioral contracts; workflow-agent owns unrelated infrastructure migrations. Never create duplicate artifacts for the same implementation.
